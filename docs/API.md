# Mustang Atlas API

Read-only JSON at `/api/v1`. Lists return `{items,total,limit,offset}`. Document IDs are opaque stable references: Ford workshop IDs such as `G1660463`, `wiring-132-001` and `connector-C2123`.

- `GET /stats`: visible document counts, media placements, distinct assets, system counts and accepted teaching coverage. Exporter-only “About this Manual” entries are excluded consistently from counts and public routes.
- `GET /systems?engine=`: `{items:[{id,title,description,introduction?,howItWorks?,documentCount,sections:[{id,code,title,count,documentCount,kinds,engines}],engines}],total,engine,engineOptions}`.
- `GET /documents?q=&system=&kind=&engine=&section=&limit=30&offset=0`: searchable document summaries. Kinds are `repair`, `diagnosis`, `overview`, `specifications`, `general`, `wiring`, `connector`. The section filter accepts an exact section code or title.
- `GET /documents/:id?engine=&year=`: structured article, original illustrations, optional accepted teaching content, learning context, calculator metadata and parts information. `?source=1` no longer exposes a separate source representation.
- `GET /documents/:id/circuit-context?engine=`: the same wiring explanation returned as `document.circuitContext`, with applicability; non-wiring/unknown documents return 404.
- `GET /documents/:id/parts?engine=&year=`: the same parts information available in detail. See [PARTS.md](PARTS.md).
- `GET /documents/:id/maintenance?engine=&year=`: `{documentId,maintenance}` using the same guidance as article detail. Maintenance is `null` when no verified component rule applies. Unknown articles return 404; incompatible engine selections return no guidance. See [MAINTENANCE.md](MAINTENANCE.md).
- `GET /documents/:id/workshop-guides?engine=&year=`: `{documentId,items}` with up to eight compatible guide cards, also returned as article detail's `workshopGuides`. Discovery requires an exact match in a validated guide's procedure links, not a keyword or incidental evidence reference. Earlier procedure positions rank first, then title. These are related care/repair guides, not a claim that each guide is the article's exact job. Unknown articles return 404; no matches return an empty array.
- `GET /maintenance?q=&category=&system=&taskType=&difficulty=&engine=&year=&limit=60&offset=0`: searchable maintenance/workshop guide cards, categories, facets and normal schedule entry. Cards include `href`, `thumbnail`, `interval`, `systemId`, `taskType`, `difficulty` and explicit engine/year/equipment applicability. `system` uses the 13 `/systems` IDs; `taskType` is `maintenance|diagnostics|repair|overhaul`; `difficulty` is `basic|intermediate|advanced|specialist`. Omitted/empty/`all` classification filters select all; unsupported values return 400. Search includes authored `searchTerms` synonyms. Maximum page size remains 100.
- `GET /maintenance/schedule?engine=&year=`: oil-life explanation, interval groups and internal guide links. An incompatible engine/year receives no schedule intervals.
- `GET /maintenance/:id?engine=&year=`: original explanations, timing, preparation, checks, warning signs, related guides and matching repair articles. Optional `diagnostics:[{finding,meaning,next}]` and `verification:[{title,body}]` return empty arrays when absent. Procedure links include `applicability` (engines, years, selected-vehicle matches, and equipment/market when known); these intersect the article, guide and optional narrower procedure scope. Article references and thumbnails are verified against their stored source revision. Unknown guides return 404. See [MAINTENANCE-GUIDES.md](MAINTENANCE-GUIDES.md).
- `GET /glossary?q=&engine=&limit=100&offset=0`: shared term index; `GET /glossary/:id?engine=` returns explanations and relevant article references/illustrations.
- `GET /media/:filename`: original raster illustration or sanitized vector drawing.
- `GET /healthz`: service and visible catalog readiness.

The global engine values are `all`, `2.3L`, `3.7L`, `5.0L`, and `5.2L`. Unknown/shared applicability stays available; definitely incompatible articles are excluded from lists, searches, subsection counts and related/reference arrays. Metadata comes from article/section headings and explicit transmission application evidence, never incidental engine mentions inside instructions. The 6R80 and MT82 transmission/control chapters cover 2.3/3.7/5.0; 3160 chapters cover 5.2. Shared clutch chapters remain broad because their MT82 section label also contains explicitly titled 5.2L articles. A direct detail request remains accessible with `applicability.matchesSelectedEngine:false`, so a client can offer an engine switch.

Summary shape: `{id,title,systemId,section:{id,code,title},operation,kind,engines,applicability:{engines,scope,selectedEngine,matchesSelectedEngine},summary,teachingStatus,learningStatus,thumbnail}`. A thumbnail is either null or a quality-resolved, substantive image placed in that same article, with `documentId` and `kind`. Scalable connector faces and wiring drawings are eligible even when their native SVG viewport is small; tiny raster tool icons are excluded. Detail adds `blocks`, `media`, `related`, optional `introduction`, `requirements`, `calculator:{type}`, and `parts`.

Public API responses omit source hashes, filesystem paths, PDF URLs, source blocks and private editorial audit metadata. The `/source` route returns 404; provenance and original files remain private for validation and generation. Internal cross-references resolve to Markdown links such as `[Direct Clutch Assembly](#/document/G1686434)`, using title, section, operation and compatible engine evidence. Referral links honor the selected engine, retain shared/unspecified references, and label known engine applicability in their visible text. All-engine mode shows each distinct variant once per text block; repeated destinations are deduplicated. This applies both to extracted referrals and authored Markdown links, including learning context. Incompatible links embedded in an actual instruction become plain text so the action is preserved; standalone referral sentences can be omitted. Unresolvable reference boilerplate is removed while surrounding actions, figures, safety notices, table structure and technical values remain. Empty/duplicate reference-only headings are collapsed. Technical uses of “manual transmission” remain unchanged.

Teaching status is `source` until a complete accepted overlay matches the current private source hash; `complete` means a Codex editorial overlay passed independent checks, not human review. Rendered source-derived blocks remain available while rewriting continues.

Every block has a stable `id` and `type`. Recursive block types:

- `heading`: `level`, `text`.
- `paragraph`: `text`, optional editorial `why`.
- `safety`: `severity` (`warning`, `caution`, `notice`, `note`), `text`.
- `step`: original `number`, `text`, `children` in source order, optional `why`.
- `list`: `ordered`, `start`, `items`; each item is `{id,type:"list-item",text,children}`.
- `table`: `rows:[{cells:[{text,colSpan,rowSpan,header,blocks:[]}]}]`; nested cell blocks retain figures, lists and sub-tables. Source cell text and technical values remain unchanged by editorial overlays.
- `media`: `mediaId` referencing the document's media array.
- `video`: `videoId`, `url`, `title`, `mime`; an available local MP4 with native playback controls.
- `video-link`: the same fields for a verified external Ford video player, opened explicitly by the user.
- `missing-media`: `text` describing a missing source image reference.

Media entries: `{id,url,mime,width,height,caption?,legend?:[{color,label}]}`. All source illustrations retain their original order and associations. Empty style-only layout tables are unwrapped. Diagrams render as images rather than executable inline SVG. Source URLs, local paths, raw HTML, CSS, scripts and JavaScript links are never returned.

Verified larger originals can be selected through `data/media-quality.json`: `{version:1,assets:{"/media/<original-sha256>.jpg":{url:"/media/<native-sha256>.jpg",mime:"image/jpeg",width:1902,height:1250,sourceWidth:580,sourceHeight:381}}}`. The map is reloaded when its file identity changes. Safe local asset URLs, matching original dimensions, a larger image and an existing target file are required; invalid or unavailable overrides fall back to the original. Document and glossary media share the same resolver. Upgraded entries retain their original `id`, caption and associations, and add `originalUrl`, `sourceWidth`, `sourceHeight` and `quality:"native-source"`. A narrowly marked `sourceKind:"svg-embedded-raster-repair"` permits an SVG-to-SVG replacement with exactly unchanged geometry, returning `quality:"restored-source"`; this cannot enable same-size raster replacements. Public dimensions describe the selected image. Optional private download provenance is not returned. This presentation layer does not change catalog source hashes, blocks, PDFs or editorial acceptance. The Codex worker resolves the same map when preparing each job's image inputs.

`node scripts/upgrade-pdf-media.mjs` produces lossless 4096px-long-edge renders of the vector Metrics reference and writes proposed overrides to `work/media-quality-metrics.json`. It never writes the live quality map, so it can run safely during bulk recovery. Its PDF and catalog access are read-only; generated PNGs use content-addressed media filenames. Raster-containing pages are rejected to avoid presenting an enlarged low-resolution image as recovered detail. Merge the proposal only after the bulk map writer has stopped.

Editorial files: `content/guides/<id>.json` and `data/guides/<id>.json`, containing `{documentId,sourceHash,title?,introduction?,edits:[{blockId,text,why?}],requirements:[{category,items:[{name,detail}]}],status:"complete",checks:{passed:true},checkedAt?,model?}`. Edits replace plain text leaves only, retaining every original media/table block. Full accepted coverage, valid unique block IDs and exact source hash are required. The API does not generate content or contact any AI provider.

`content/glossary.json`: `{version:1,terms:[{id,name,aliases,definition,details,category,sourceRefs:[{documentId}],mediaRefs:[{documentId,mediaId,caption?}],relatedTermIds:[]}]}`. `content/systems.json`: `{version:1,systems:[{id,title?,description,introduction,howItWorks:[{title,body}],sourceRefs:[{documentId}]}]}`.

Ingestion: `node scripts/ingest.mjs --source /path/to/source --data data`. The catalog and an ingestion manifest are written under data. Catalog reads do not mutate SQLite; this supports a read-only production mount. Search tokenizes and quotes user input and binds all SQL parameters. Pagination is bounded, API responses are JSON, and no write endpoint is exposed.

The thirteen system titles remain short navigation labels. Authored explanatory headings are returned separately as `contextTitle`; `introduction` and `howItWorks` provide the system teaching context. Ingestion uses TOC references rather than repeated HTML metadata IDs, keeping engine variants distinct. Duplicate shortcut documents receive a deterministic path suffix.

Audit the complete catalog and its exact media placements with `node scripts/audit-catalog.mjs`. Check source-text preservation with `node scripts/audit-source-text.mjs --source /path/to/manual`; this independently compares all imported HTML body text, in order, with the parsed blocks after removing navigation, source headers, scripts, styling and inactive form controls. Whitespace is normalized. Reports are saved under data.

`sourceHash` includes the source-file hash, parsed blocks and media metadata; a parser change therefore invalidates prior editorial overlays. Diagnostic prose inside tables is represented as editable cell blocks; short technical values and labels stay immutable. Non-li content in malformed source lists, table captions, safety severity and every original media placement are preserved.

`GET /abbreviations?q=` returns the complete source acronym index with resolved references. Unambiguous expansions also appear in `/glossary` when their name does not collide with an authored term or alias. They use `editorial.kind: "source-expansion"` and an exact source expansion as their definition; fuller authored explanations take precedence. Accepted document guides supply their plain-language title and introduction in catalog cards as well as the detail response.

Publication validation is shared by the API and Codex worker in `server/guide-validation.mjs`. The API independently checks identity, source hash, complete block coverage, numeric values, recognized quantity/unit pairs, and explanatory metadata; a saved `checks.passed` flag alone is insufficient. Unit notation equivalents such as `lb.ft` and `lb-ft` are accepted, while changed units, new per-action numbers and lost temperature signs are rejected. Markdown link targets do not count as technical values; visible link labels still do. Introductions, requirements and explanations are checked against the document’s visible source/table evidence and its selected curated context. These deterministic checks are not a human technical review.

Topic learning context is separate from the full procedure rewrite. Detail responses add `learningStatus:"complete"|"pending"` and, only for an accepted mapping, `learningContext:{version:1,title,summary,sections:[{id,title,body}],relatedTerms:[{id,name}],sourceRefs:[{documentId,title,kind}],status:"complete"}`. List responses include `learningStatus` and prefer the mapped context summary over exporter text, while accepted guide introductions still take precedence. Stats expose `contextualizedDocuments` and `contextualizationStatus:"complete"|"in_progress"` independently from `rewrittenDocuments` and `teachingStatus`. Complete contextualization does not mean that every procedure has been rewritten or human reviewed.

Authored context lives in `content/topic-contexts.json`: `{version:1,topics:[{id,title,summary,sections:[{id,title,body}],relatedTermIds:[],sourceDocumentIds:[]}],documents:{"<documentId>":{topicId,sourceHash,summary?}}}`. Each document mapping must match its current catalog source hash. Topic and section IDs must be safe and unique; all source document and glossary references must resolve. Unambiguous source abbreviation IDs from the shared glossary are also supported. Titles are limited to 240 characters, summaries to 2000, section bodies to 24000, sections to 16, glossary references to 64 and source references to 256. HTML, control characters and external/executable URL protocols are rejected. Ordinary Markdown is supported; navigable references are supplied through the resolved reference arrays. Invalid, stale or missing content produces no placeholder context and leaves the article reader usable. Context and glossary file changes invalidate the cached catalog automatically.

Run `node scripts/audit-contexts.mjs` to validate all mappings and report source coverage, rejected records and missing document IDs once. It exits unsuccessfully for any rejected or missing context. Optional `--data` and `--content` arguments select another release. This is a structural and provenance audit; editorial correctness still requires checking the explanations against their cited sources.

Validation results are cached by source hash, guide file identity and curated content identity, and invalidated on file changes. Worker restart revalidates published files and saved partial edits with the current rules. Invalid partial edits are returned to the work queue rather than being treated as completed. Small documents include their original illustrations in full; longer documents select media in source order around each text chunk, including following action illustrations and bounded preceding context. Batches are split around a 24-image budget where possible; required images are not silently discarded.

Run `node scripts/audit-public-catalog.mjs` to verify every visible article for dangling public links, leaked source-interface copy, numeric preservation around reference removal, exact media/step/safety/table structure, and engine/system/subsection count consistency. The read-only audit writes `work/public-catalog-audit.json`.

Wiring context uses `{documentId,title,summary,mode,scope,components,circuits,connections,continuations,readingGuide,coverage}`. `mode:"terminal-map"` matches explicitly printed vector circuit/cavity IDs to connector assignments; it does not infer routing, junctions or current flow from text proximity. `reference-map` covers drawings without circuit data. Reviewed curated records may supply verified connections, guarded by exact document, SVG and supporting-reference hashes. `coverage.topologyVerified` distinguishes those cases. Known full-sheet applicability can be added only from reviewed, hash-bound evidence; for example, the 2.3L header of wiring-033-002 applies to that whole sheet. Branch-local qualifiers remain local.

Reviewed image-only actions may receive captions from `content/illustrated-steps.json`. Application requires the exact private article hash, an actually blank numbered step, the immediately following original media ID and URL, and an empty current text field. Existing authored action text wins. This adds readable guidance without changing immutable source blocks or moving an illustration to another action.

Article detail also includes `maintenance:{documentId,title,scope,items}` or `null`. Each item separates `what`, `when` and `why`, with optional steps/notes, a `kind` of `scheduled`, `inspection` or `condition-based`, and explicit year/engine/equipment applicability. No replacement interval is inferred from a repair procedure. Private supporting article hashes remain in the curated catalog; public schedule links identify the applicable Ford owner guidance. The reader places relevant care after the repair/parts content and adds it to the article contents. No empty maintenance panel is rendered.

Recovered procedure videos are bound to the exact article hash and original play-control asset in `content/procedure-videos.json`. Ten MP4s are stored as content-addressed `/media/*.mp4` files; three external Ford players cover four additional placements. Detail exposes only public playback metadata in `videos` and replaces the original control at its exact block position. Decorative play controls are excluded from article images, parts diagrams and thumbnails. Missing or stale video evidence never creates a nonfunctional player. `scripts/recover-procedure-videos.mjs --source <export-directory>` verifies public source responses, file lengths and MP4 headers before storing hashed files; media files remain outside Git.

Torque highlighting is presentation-only. It preserves all values, units, bolt/nut labels and stage/angle order; it does not calculate conversions or invent tightening instructions. Punctuation-only list and step text is omitted while attached instructions, diagrams, videos and meaningful table symbols remain available.

The guide list returns `facets:{systems,taskTypes,difficulties}`, each an array of `{id,title,count}`. Facet counts respect engine/year, text query, category and the other two classification filters while excluding their own selection. Existing `categories` counts continue to describe the engine/year-compatible catalog, regardless of query or classification filters. The response echoes `system`, `taskType` and `difficulty`; pagination applies after filtering.

`content/maintenance-guides.json` remains the authoritative source of existing categories, guide routes and the normal schedule. Optional `content/workshop-guides.json` is `{version:1,guides:[],evidence:{}}`, limited to 32 MiB. Both files are reloaded when their file identity changes. Workshop records require explicit valid classification fields; the original 46 guides receive deterministic ID-based system/task/difficulty defaults without rewriting their content. Routine care defaults to maintenance/basic; named fluid/filter/belt service is intermediate, the existing advanced category is advanced, and A/C performance/leak testing is specialist. Diagnosis and repair IDs are classified explicitly. Unknown legacy IDs use their first procedure's system, with general as the final fallback.

Guide IDs must be unique across both files; an ambiguous ID is withheld rather than choosing a winner. Every guide must have current, unique source-hash-bound `sourceRefs`, and each procedure or hero must belong to those references. New technical guides can use `evidence:[]` for condition-based work. Schedule membership, explicit scheduled timing and recurring mileage/time claims in `when` require supporting evidence; test durations and thresholds in diagnostic prose are not interpreted as maintenance intervals. These checks validate structure and binding; author review still establishes whether prose is technically supported. Private source hashes, evidence IDs and source references never enter public guide responses.

An optional `procedures[].mediaId` selects an illustration owned by that exact procedure. Invalid ownership withholds the guide; eligible selections appear as public `mediaId` and `thumbnail` fields after engine and video-control filtering. Defaults rank images by their component context, excluding preparation and decorative controls. A missing relevant image produces a null thumbnail instead of unrelated artwork. Images use the existing verified quality resolver, keeping the original full-resolution asset available.

Optional `thumbnailMode:"explicit-only"` disables automatic image fallback for a guide and its related procedure cards. A hero in this mode must include an exact owned `mediaId`; only that eligible, engine-compatible image is shown. A null hero produces a null guide thumbnail, even if procedure images exist. Related procedure links remain available, with a thumbnail only when their own `mediaId` is explicitly selected and eligible. This lets guides without a genuine task illustration use the UI's icon fallback without changing article media or vehicle-scope evidence. Omitted mode preserves the default image selection; other mode values are rejected.

Factory brake fitment is shared by article discovery and workshop authoring. Explicit front-caliper types and reviewed base/SVT procedure pairs have distinct application rules; generic diagnostic chapters remain shared. See [configuration evidence](WORKSHOP-FITMENT.md) for the original-equipment scope and the distinction between engine choice and an optional brake package.

Run `node scripts/audit-maintenance-guides.mjs` to audit both guide files, every pagination page, classifications, vehicle scope, local media, care/schedule links and private-field suppression. When `content/workshop-coverage.json` exists, the audit also checks document hashes, accepted guide bindings and section ranges (character offsets in `documents.text`, start inclusive/end exclusive). Coverage counts distinguish covered, pending, pointer-only and reserved documents; referenced articles alone do not count as fully explained workshop coverage.

### Editorial cover illustrations

Article `thumbnail` can now have `kind: "editorial-illustration"` and `generated: true` when no suitable image exists in that article. These original conceptual covers use `/thumbnails/*.svg`; they are not technical assembly diagrams. Existing article illustrations keep their previous metadata. Workshop guides add `cardThumbnail` for consistent listing artwork; `thumbnail` retains its existing technical-hero semantics and can remain null. Both are null for an incompatible guide configuration.
